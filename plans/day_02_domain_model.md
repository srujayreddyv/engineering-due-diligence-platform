# Day 2 Domain Model Plan

## Task

Define the formal domain model for the scoped Engineering Due Diligence
Platform without implementing application code or choosing a final persistence
schema.

## Objective

Create a single human-facing domain reference that defines the purpose,
ownership, fields, identifiers, lifecycles, transitions, relationships,
immutability, versioning, audit obligations, and incomplete-data behavior for
the seven records in the assessment workflow.

Success means a future implementation can preserve the separation between
assessment context, raw evidence, deterministic derivations, policy findings,
AI-assisted interpretation, human authority, and audit history without relying
on unstated lifecycle rules.

## Current State

Day 1 established the simulated customer, locked scope, current informal
workflow, proposed target workflow, durable architectural boundaries, and
initial success criteria. No application, database, collector, policy engine,
model integration, workflow runtime, or audit store exists.

The required relationship chain is:

`AssessmentRequest` → `EvidenceRecord` → `MetricResult` → `PolicyFinding` →
`GeneratedReport` → `HumanDecision`

`AuditEvent` records activity affecting those domain records but does not
replace them or become the authoritative source for their content.

No ADR currently exists. This task documents the already approved domain
boundaries and does not introduce a new architectural direction that requires
one.

The first read-only review used `templates/REVIEW_TEMPLATE.md` and returned
**Needs Changes**. Confirmed findings concern final-decision idempotency,
freshness at use, authoritative-record boundaries, generated-claim grounding,
further-investigation routing, successor-link integrity, the relationship
diagram, and README status. The corrections remain documentation-only.

## Assumptions

* The domain model describes logical records and invariants, not database
  tables, Python classes, transport schemas, or API payloads.
* Identifiers are opaque, globally unique, stable, and generated by
  deterministic application software. The specific identifier algorithm is
  deferred.
* A submitted request is immutable. Material context corrections or a different
  use case create a new assessment linked to the earlier one.
* Persisted evidence and downstream records are append-only. Recollection,
  recalculation, policy reevaluation, report regeneration, and later human
  review create new linked records rather than overwriting history.
* Evidence availability and freshness are explicit facts. Missing, stale,
  partial, or failed evidence never becomes an inferred favorable result.
* `request_further_investigation` is a human-owned, nonfinal disposition that
  can return the same assessment to collection and derivation.
* Approve, approve with conditions, and reject are final for that assessment
  context. A later or materially different review creates a new assessment.
* Exact evidence sources, freshness thresholds, policy content, reviewer
  authorization rules, retention periods, and storage mechanics remain to be
  defined within later scoped work.

## Acceptance Criteria

* `docs/domain_model.md` formally defines all seven required entities.
* Every entity covers purpose, ownership, required and optional fields,
  identifier strategy, lifecycle states and transitions, relationships,
  immutability, versioning, audit obligations, and failure or incomplete-data
  behavior.
* The relationship chain and the separate role of `AuditEvent` are explicit.
* Cross-entity invariants preserve evidence-before-derivation ordering,
  deterministic ownership, grounded generated claims, human decision authority,
  and complete reproducibility.
* Failed, missing, stale, and partial evidence; recollection; recalculation;
  policy changes; report regeneration; investigation requests; conditional
  decisions; context-specific reassessment; and interruption or resumption all
  have defined behavior.
* The model does not introduce a universal repository quality score.
* The document does not define a final database schema or imply that any
  runtime capability is implemented.
* `journal/day_02.md` honestly distinguishes completed documentation from
  planned implementation and records assumptions and unresolved questions.
* Cross-document review finds no contradiction with the charter, workflows,
  success criteria, or durable memory.
* Each assessment permits at most one authoritative final human decision, and
  replay or conflict behavior is explicit.
* Metric and policy records preserve every freshness status, evaluation time,
  rule version, and evidence identifier used in their result.
* Transient operation states cannot create partially valid authoritative domain
  records.
* Every material report claim cites the exact input record appropriate to its
  evidence, metric, or policy meaning.
* A generated report is valid only when structural, reference, and deterministic
  grounding validation all pass; failed or not-run required validation cannot
  advance the assessment to human review.
* Deterministic orchestration routes further investigation to the earliest
  affected stage.
* Every prior or supersedes link is same-assessment, type-correct, earlier, and
  acyclic.

## Proposed Solution

1. Establish terminology, authority boundaries, identifier conventions, and
   cross-entity invariants.
2. Define the assessment aggregate and relationship chain.
3. Define each entity using a consistent structure for fields, lifecycle,
   relationships, immutability, versioning, audit, and failure behavior.
4. Define cross-cutting behavior for incomplete evidence, repeat derivations,
   human investigation, reassessment, and workflow interruption.
5. Record implementation-neutral assumptions and unresolved questions.
6. Validate the document against the required Day 1 documents and memory.
7. Complete the Day 2 journal after the review is finished.

## Testing Strategy

No runtime tests are added because behavior is not implemented.

Documentation verification will:

* confirm all seven entities and all twelve required definition categories are
  present;
* trace the model against the project charter, current workflow, proposed
  workflow, success criteria, and architecture, pattern, and decision memory;
* inspect every lifecycle for an owner, allowed transitions, terminal behavior,
  authoritative record creation, and interruption handling;
* confirm every derived or interpreted record references its authoritative
  inputs and required versions;
* confirm final-decision uniqueness, replay, conflict, and indivisible
  completion behavior;
* confirm metric and policy results preserve at-use freshness evaluations;
* confirm material report claims use exact typed references from the fixed
  input set;
* confirm report validity and the human-review transition require all three
  deterministic validation layers to pass;
* confirm investigation routing can resume at every eligible affected stage;
* confirm successor links cannot cross assessments, reference themselves, or
  form cycles;
* confirm evidence provenance cannot be overwritten or replaced by audit
  events;
* search for hidden model authority, universal scoring, implemented-feature
  claims, and scope expansion;
* validate all local Markdown links;
* run Markdown whitespace and Git diff checks; and
* confirm no application or infrastructure artifacts changed.

## Risks

* **Premature persistence design:** Field definitions could be mistaken for a
  database schema. Mitigation: describe logical attributes and explicitly defer
  storage representation.
* **Lifecycle ambiguity:** Multiple status dimensions could permit invalid
  transitions. Mitigation: separate workflow state, collection outcome, and
  freshness, then list allowed transitions.
* **History loss:** Recollection or regeneration could appear to replace prior
  facts. Mitigation: make authoritative records append-only and link successors
  to predecessors.
* **Hidden AI authority:** Report generation could be interpreted as a policy
  or decision step. Mitigation: make deterministic validation authoritative and
  keep human dispositions separate.
* **Scope expansion:** Condition tracking, monitoring, broad integrations, or a
  final database design could enter the model. Mitigation: define only the
  record required for the scoped assessment and defer operational extensions.
* **False completeness:** Documentation could imply implemented behavior.
  Mitigation: label the model as a design contract for planned implementation.
